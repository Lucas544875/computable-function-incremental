## 1. コンセプト

**「計算可能関数を工場で組み立てる」** インクリメンタルゲーム。

プレイヤーは種関数(ゼロ・後者・射影)の機械だけを持って始め、**合成・原始帰納法・最小化** の 3 つの操作で、加算 → 乗算 → 冪乗 → … → 万能関数へと関数を組み上げていく。Factorio が「鉱石 → 鉄板 → 歯車 → …」と製品を積み上げるのに対し、本作は「`S` → `add` → `mult` → `exp` → …」と **関数** を積み上げる。

### 1.1 デザインの柱

| 柱 | 内容 |
|---|---|
| 数学的に正直 | 盤面で組んだものは、そのまま μ-再帰関数の項として解釈できる。ごまかしの「魔法の機械」は置かない |
| 抽象化が報酬 | 組んだ工場を 1 個の機械に **カプセル化** して再利用できる。Factorio のブループリント+関数定義 |
| 停止しないことが遊びになる | 最小化(μ)は停止しないことがある。詰まり・暴走を設計で回避することがパズルになる |
| 数の爆発が自然に起きる | 加算 → 乗算 → 冪乗 → テトレーションという増大度の階層が、そのままインクリメンタルの成長曲線になる |

### 1.2 想定プレイヤーと前提

- 対象: Factorio / Shapez 系の自動化ゲームと、計算理論・プログラミングに興味がある人
- 数学的内容だけを追いたい人には、待ち時間のない **探究モード**(§4.11)を用意する
- 上級目標として、算術化による第一不完全性定理の証明を組み立てる **不完全性コース**(§4.12)を用意する
- プラットフォーム: **デスクトップ Web ブラウザ**(マウス+キーボード)。モバイルは対象外
- シングルプレイ、サーバーなし、セーブはローカル
- UI 言語: 日本語(文言は辞書に分離し、後から英語を追加可能にする)

## 2. 数学モデル

ゲーム内の関数はすべて `ℕ^k → ℕ` の部分関数で、次の項(Term)で表現する。

| 構成子 | 記法 | アリティ | 意味 |
|---|---|---|---|
| ゼロ | `Z` | 0 | `Z() = 0` |
| 後者 | `S` | 1 | `S(x) = x + 1` |
| 射影 | `P[n,i]` (1 ≤ i ≤ n) | n | `P[n,i](x₁..xₙ) = xᵢ` |
| 合成 | `C(f; g₁..gₘ)` | k | `f(g₁(x⃗), …, gₘ(x⃗))`。`f` は m 引数、各 `gⱼ` は k 引数 |
| 原始帰納法 | `R(g, h)` | k+1 | `f(x⃗,0) = g(x⃗)`、`f(x⃗,n+1) = h(x⃗, n, f(x⃗,n))`。`g` は k 引数、`h` は k+2 引数 |
| 最小化 | `M(f)` | k | `μy[f(x⃗,y) = 0]`。`f` は k+1 引数。`f(x⃗,i)` が i < y で定義され非零、`f(x⃗,y) = 0` となる最小の y。なければ未定義(停止しない) |
| 参照 | `Ref(id)` | 定義による | カプセル化済み関数(ブループリント)への参照 |

- 項は **アリティ検査** を通ったものだけが有効。検査はカプセル化時・スロット装着時に行う
- `Ref` は循環参照を禁止する(再帰は `R` と `M` だけが担う)
- 値は `bigint`。ただし盤面を流れる値には **帯域幅(ビット長上限)** があり、超えたトークンは破棄される(初期 64bit、研究で拡張)

### 2.1 コストモデル

各評価には **ステップ数(コスト)** が定義され、機械の処理時間を決める。

| 項 | コスト |
|---|---|
| `Z`, `S`, `P` | 1 |
| `C(f; g⃗)` | `Σ cost(gⱼ) + cost(f)` |
| `R(g,h)` を n で評価 | `cost(g) + Σ_{i<n} cost(h の i 回目) + n` |
| `M(f)` が y で停止 | `Σ_{i≤y} cost(f(x⃗,i)) + y + 1` |
| 定理化済み `Ref`(§4.6) | カタログ定義の閉形式コスト(例: `add` は 1) |

機械の処理時間は `ceil(コスト / 機械速度)` tick。

## 3. ゲームループ

```
契約を受ける → 入力港から引数が流れてくる → 機械とベルトで関数を実装
   → 納品港に正しい値を届ける → QED(通貨)獲得
   → 機械増設・研究 → カプセル化・定理化で高速化 → より難しい契約へ
```

- **短期(秒〜分)**: ベルトを引き、機械を置き、スループットを上げる
- **中期(分〜時間)**: 新しい関数を実装してカプセル化し、上位の契約を解禁する
- **長期(時間〜日)**: 研究ツリーを進め、階層昇格(プレステージ)で次の関数クラスへ

## 4. ゲームシステム

### 4.1 盤面とトークン

- 正方グリッド(初期 32×32、研究で拡張、最大 128×128)
- ベルト上を **トークン** が流れる。トークン = `{ 値: bigint, 伝票: JobId | なし }`
- **伝票(JobId)**: 入力港が引数の組を 1 つ出すたびに発番される。機械の出力は入力の伝票を引き継ぐ
  - 複数入力の機械は、**同じ伝票のトークンが全ポートに揃ったとき** に処理を開始する(各ポートに小バッファを持つ)
  - `Z` 源のトークンは伝票なし(ワイルドカード)で、どの伝票とも組める
  - これにより並列ラインで順序が入れ替わっても正しさが壊れない

### 4.2 機械一覧

| 分類 | 機械 | 入力 → 出力 | 説明 |
|---|---|---|---|
| 種 | ゼロ源 `Z` | 0 → 1 | 一定間隔で `0` を出す |
| 種 | 後者機 `S` | 1 → 1 | `n → n+1` |
| 種 | 射影機 `P[n,i]` | n → 1 | i 番目だけ通し、残りを捨てる |
| 物流 | ベルト / 地下ベルト | — | トークンを運ぶ |
| 物流 | 複製器 | 1 → 2 | 同じトークンを 2 本に複製(合成+射影で正当化できる操作の省略形) |
| 物流 | 分配器 / 合流器 | — | 並列化用。伝票単位で振り分ける |
| 物流 | 廃棄口 | 1 → 0 | 不要なトークンを捨てる |
| 構成 | 帰納炉 `R` | k+1 → 1 | スロットに `g` と `h` のブループリントを装着。`(x⃗, n)` を受け取り n 回反復する |
| 構成 | 探索塔 `M` | k → 1 | スロットに `f` を装着。y = 0,1,2,… と探索する。**打ち切りステップ数** を設定でき、超えたら入力を破棄する |
| 構成 | 関数機 `Ref` | k → 1 | カプセル化したブループリントを 1 マス機械として置く |
| 入出力 | 入力港 | 0 → k | 契約の引数組を伝票つきで出す |
| 入出力 | 納品港 | 1 → 0 | 値を受け取り、伝票に対応する正解と照合する |

**合成** は専用の機械を持たない。ベルトで出力を入力に繋ぐこと自体が合成である。

### 4.3 カプセル化(ブループリント)

1. 盤面の矩形範囲を選択し、**仮入力ポート**(k 個、順序つき)と **仮出力ポート**(1 個)を指定する
2. 範囲内の機械と配線を DAG として抽出し、項に変換する(各機械 = `C(機械の関数; 入力元の項…)`、仮入力 = `P[k,i]`)
3. 検査: 範囲内に閉路がないこと、全ポートが接続されていること、アリティが合うこと
4. 名前をつけて保存 → 関数機として設置可能になり、帰納炉・探索塔のスロットにも装着できる

- ブループリントは項として保存する(盤面レイアウトは再編集用に別途保持)
- 関数機の処理時間は §2.1 のコストから決まる。盤面で組むより省スペースだが、内部は並列化されない

### 4.4 契約

契約 = 「この関数を実装せよ」という注文。

- 定義: `{ 目標関数, アリティ, 入力範囲, 報酬単価, 解禁条件 }`
- 入力港は入力範囲から(シード付き乱数で)引数組を生成して流す
- 納品港での判定:
  - 正解 → 報酬単価 × 倍率の QED を獲得
  - 不正解 → その伝票は報酬なし、連続正解ボーナスがリセット
  - 伝票の重複・混線(異なる伝票の合成) → 不正解扱い
- 同時に稼働できる契約数は研究で増える(初期 1)
- **入力範囲の拡張**: 契約ごとに範囲を広げるアップグレードがあり、単価は上がるが帰納の反復回数も増える

#### 契約カタログ(抜粋)

| 段階 | 解禁要素 | 関数例 |
|---|---|---|
| T0 種 | Z, S, P, ベルト | `const₀`, `id`, `+2`, `swap` 系の射影 |
| T1 帰納 | 帰納炉、カプセル化 | `add`, `pred`, `monus`(切り捨て減算), `mult`, `sgn`, `is_zero` |
| T2 原始帰納 | 複数契約、定理化 | `exp`, `fact`, `min`/`max`, `eq`, `div`, `mod`, `is_prime`, 有界和・有界積 |
| T3 最小化 | 探索塔 | `isqrt`, `log`, 逆関数、`nth_prime`, コラッツ停止時間 |
| T4 符号化 | 帯域幅拡張 | 対関数 `pair`/`unpair`, 列の符号化、`ackermann` |
| T5 万能 | — | 万能関数 `U(e, x)`(本編の最終目標) |
| G0〜G6 | 図式、項エディタ | 不完全性コース(§4.12)。T2 以降に分岐する上級目標 |

- 契約の入力は「範囲からの乱数」に加えて **入力生成器**(整形式の論理式の符号、正しい証明と壊れた証明など、構造を持つ入力を作る関数)でも定義できる

### 4.5 経済

| リソース | 入手 | 用途 |
|---|---|---|
| **QED**(通貨) | 納品 | 機械の設置、盤面拡張、契約アップグレード |
| **定理点** | 契約の初回達成・定理化 | 研究ツリー |
| **公理点** | 階層昇格(§4.8) | 永続アップグレード |

- 機械の価格は種類ごとに固定(設置数で上がらない)。成長の制約は **盤面の広さ** と **スループット** に置く
- 機械の撤去は全額返金(試行錯誤を罰しない)
- QED は巨大数になるため `Decimal`(break_infinity 系)で保持する

### 4.6 定理化(加速)

素朴な原始帰納法は遅い(`mult` は `add` を n 回、`exp` は `mult` を n 回…)。これを解消する中核の成長要素。

- あるブループリントで契約を **規定回数連続で正解** すると、そのブループリントは **定理化** される
- 定理化されたブループリントは、カタログ関数のネイティブ実装と閉形式コストで評価される(例: `add` が 1 ステップになる)
- 以降、その関数を部品に使う上位の関数がすべて高速化する → 「下位を自動化して上位に進む」ループが成立する
- カタログにない自作関数は定理化されず、常にインタプリタで評価される

### 4.7 研究ツリー

定理点を消費して解禁する。主な枝:

- **構成**: 帰納炉 → カプセル化 → 探索塔
- **物流**: ベルト速度、地下ベルト、分配器、盤面拡張
- **機械**: 機械速度、バッファ容量、帯域幅(64 → 256 → 1024bit …)
- **運用**: 同時契約数、オフライン進行の上限時間、統計パネル

### 4.8 階層昇格(プレステージ)

- Grzegorczyk 階層になぞらえ、`E⁰ → E¹ → E² → …` と昇格する
- 昇格条件: 現階層の代表関数(E¹: `add`、E²: `mult`、E³: `exp` …)の契約で規定量を納品する
- 昇格すると盤面・QED・研究がリセットされ、公理点を得る。**ブループリントは保持**(定理化はリセット)
- 公理点で永続強化(初期機械速度、定理化に必要な正解数の削減など)
- MVP には含めない(v1.0 の範囲)

### 4.9 オフライン進行

- オンライン中に契約ごとの平均収入レート(直近 5 分の移動平均)を記録する
- 復帰時に `レート × 経過時間 × 効率(初期 50%)` を付与する。上限時間は初期 2 時間、研究で延長
- オフライン中の盤面シミュレーションは行わない

### 4.10 停止しない計算の扱い

- 探索塔が打ち切りステップ数に達したら、入力を破棄して次へ進む(その伝票は未納品)
- 打ち切り未設定の探索塔は占有されたままになる(プレイヤーに「暴走中」と表示)
- 帰納炉・関数機にも安全上限(グローバルなステップ上限)を設け、超過時は破棄して警告を出す

### 4.11 探究モード(高速モード)

数学的内容そのものに興味がある人向けの、**待ち時間がほぼないモード**。関数を正しく構成できたかどうかだけが進行条件になり、スループットと通貨稼ぎは進行に関わらない。

- セーブスロット作成時に「工場モード(通常)」か「探究モード」を選ぶ。工場 → 探究への変換は可能、逆は不可
- 扱う数学的内容(構成子、契約カタログ、コース)は両モードで同一

| 項目 | 工場モード | 探究モード |
|---|---|---|
| 契約の達成条件 | 納品を重ねて QED を稼ぐ | **検査に 1 回合格すれば達成**(下記) |
| QED・機械価格 | あり | なし(機械・盤面拡張はすべて無料) |
| 研究 | 定理点を消費 | 契約達成で自動解禁(前提関係だけ残る) |
| 定理化 | 規定回数の連続正解 | 検査合格と同時 |
| 機械の処理時間 | コストに比例 | 常に 1 tick。ベルトは最高速 |
| 帯域幅 | 研究で拡張 | 上限なし(安全上限のみ) |
| 項エディタ | 研究で解禁(終盤) | 最初から使える |
| オフライン進行・階層昇格 | あり | なし(階層は到達記録として表示のみ) |

**検査**: ブループリントを盤面で流さず評価器で直接実行し、契約の検査入力すべてについてカタログの参照実装と結果を比べる。

- 検査入力は契約ごとに定義する(小さい範囲の全数+境界値+乱数サンプル)
- 合格/不合格は即時に返す。不合格時は **最小の反例**(引数、期待値、実際の値)を表示する
- ステップ予算を超えた入力は「予算内に停止せず」と表示し、不合格とする
- 工場モードでも検証パネル(§5)から同じ検査を実行できるが、達成条件にはならない

**項エディタ**: 盤面を使わず、テキストで関数を定義する手段。

- 記法は §2 の項そのもの。例: `mult = R(Z, C(add; P[3,1], P[3,3]))`
- 入力中にアリティ検査の結果を表示する。保存するとブループリントになり、盤面で組んだものと区別なく使える
- 盤面で組んだブループリントも項として表示・編集できる(編集後は盤面レイアウトを失う)

待ち時間が残りうるのは評価器の実行時間だけなので、検査は Worker で実行し、進捗表示と中断ボタンを付ける。

### 4.12 不完全性コース

上級目標。**算術化(ゲーデル数化)によってゲーデルの第一不完全性定理の証明を組み立てる。** 証明に現れる原始帰納的関数をプレイヤーが実際にすべて構成し、最後にゲーデル文のゲーデル数を計算する機械を完成させる。

- 解禁条件: T2(原始帰納)達成で G0 が、T4(符号化)達成で G4 以降が開く。T5(万能関数)とは独立に進められる
- 両モードで遊べるが、探究モードを主な想定とする

#### 対象とする定理

> **T を Robinson 算術 Q とする。T が ω 無矛盾ならば、T ⊬ G かつ T ⊬ ¬G となる文 G が存在する。**

- 体系に Q を選ぶ理由: 非論理公理が有限個で、公理の判定関数が小さく済む。結果は Q を含む再帰的公理化可能な理論に一般化できる(ノートで解説)
- 論理は Hilbert 流(論理公理図式+推論規則 MP・汎化)
- Rosser による「無矛盾」への強化はボーナス課題。第二不完全性定理は対象外

#### 符号化

- 形式言語の記号は 13 個: `0 S + · = ¬ → ∀ ( ) v ' #`(変数は `v`, `v'`, `v''`, …。`#` は証明列の区切り。`∃ ∧ ∨` は略記)
- 記号列のゲーデル数は **全単射 13 進法**(各記号を 1〜13 の桁とする。空列は 0)。記号列と自然数が 1 対 1 に対応し、数の大きさは列の長さに比例する
- 素数冪による符号化は採らない(数が大きくなりすぎ、評価できないため)。ノートで原論文の方式として紹介する
- 真偽は特性関数で表す(真 = 1、偽 = 0)

#### 追加要素: 図式

**関数スロットを持つブループリント**。有界量化などの「関数を引数に取る構成」を一度だけ `R` から導出し、以後は部品として使えるようにする。

- 図式は項に穴(関数変数)を空けたもの。スロットに関数を装着すると通常の項に展開される。数学モデル(§2)は拡張しない
- 図式も検査に合格すれば定理化され、ネイティブ実装(早期打ち切りつき)で評価される

#### 段階

| 段階 | 主題 | 構成する関数(抜粋) |
|---|---|---|
| G0 | 図式 | 有界和・有界積、有界 ∃/∀、有界 μ、場合分け、累積帰納法 |
| G1 | 記号列 | `len`(長さ)、`at`(i 番目の記号)、`concat`(連結)、`slice`(部分列)、`occurs`(出現) |
| G2 | 構文 | `num`(n ↦ 数項 `S…S0` の符号)、`is_var`、`is_term`、`is_formula`、`is_free`、`subst`(代入) |
| G3 | 証明 | `is_logic_axiom`、`is_q_axiom`、`mp`、`gen`、**`prf(p, x)`**(p は x の証明である) |
| G4 | 表現可能性 | `beta`(β 関数)、**`repr`**(本作の原始帰納的な項の符号 ↦ それを Q で表現する論理式の符号) |
| G5 | 対角化 | `diag(x) = subst(x, v, num(x))`、**ゲーデル文の符号 `g`**(0 引数のブループリントとして構成) |
| G6 | 定理 | 証明ノートの完成 |

- G3 の検査入力には、Q での実際の証明(`0=0`、`SS0+SS0=SSSS0` など)と、それを 1 か所壊した偽の証明を使う。プレイヤーの `prf` が証明検査器として実際に動くことを確かめられる
- G4 の `repr` は「本作の項を算術の論理式へ翻訳するコンパイラ」をゲーム内の関数として作る課題で、コース最大の山場。`diag` と `prf` 自身を `repr` に通すことで、G5 で必要な論理式が得られる
- G5 の `g` は、`repr` で得た論理式から「x の対角化は証明できない」を表す論理式 A(v) を作り、`diag(⌜A⌝)` として計算する。プレイヤーの機械が出した数を参照値と照合する

#### 構成するものと引用するもの

ゲームが検査できるのは **計算** であり、メタ数学の論証そのものではない。この境界をゲーム内で明示する。

| 区分 | 内容 | ゲームでの扱い |
|---|---|---|
| 構成する | G0〜G5 の全関数、ゲーデル文の符号 `g` | 参照実装との照合で検査 |
| 構成する | 「`prf` は原始帰納的である」 | プレイヤーの項が `M` を含まないことを機械的に確認 |
| 引用する | 表現可能性定理(`repr` の出力が実際に Q で元の関数を表現すること) | 補題カードとして提示。証明の概略をノートに載せる |
| 引用する | 対角化から「T ⊢ G ⇔ T ⊢ ¬Prov(⌜G⌝)」を導く論証、ω 無矛盾性からの結論 | 証明ノートの文章。各行がプレイヤーの構成物にリンクする |

**証明ノート**: 定理の証明を番号つきの行で示す画面。各行は「構成済み(プレイヤーのブループリントへのリンク)」「引用(補題カード)」「未達」のいずれかで、コースの進行表を兼ねる。全行が埋まるとコース完了。

#### 別証明(ボーナス)

T5 の万能関数 `U` を完成させたプレイヤー向けに、停止問題を経由する証明を用意する: 「T が健全かつ完全なら、証明の探索(`M` と `prf`)で停止問題が決定できてしまう」。この決定手続きを実際に組み、対角化で破綻する入力を構成する。

#### 評価可能性の設計指針

論理式の符号は数百〜数万ビットになり、値までの反復(`R` を符号の値の回数だけ回す)は実行できない。

- カタログの参照定義は、**符号の値ではなく記号列の位置・長さについて量化する** 形で与える(例: 「x が y に出現する」は「∃i, j ≤ len(y): slice(y, i, j) = x」)。こうすればコストは長さの多項式に収まる
- 契約の説明文でこの形の定義を提示し、値について量化した定義は検査のステップ予算で不合格になるようにする(効率のよい上界を選ぶこと自体を課題にする)
- 検査入力は短い記号列を中心に構成し、定理化後はネイティブ実装で大きい入力を扱う

## 5. UI / UX

- **メイン画面**: 盤面(パン・ズーム)+ 下部ホットバー(機械選択)+ 右パネル(選択中の機械/契約)+ 上部バー(QED・定理点・収入レート)
- **操作**: 左クリック設置、右クリック撤去、ドラッグでベルト敷設、`R` 回転、`Q` スポイト、`Ctrl+Z` 取り消し、範囲選択 → カプセル化
- **関数ライブラリ**: 保存済みブループリントの一覧。項の表示(`mult = R(Z, C(add; P[3,1], P[3,3]))`)、アリティ、定理化状態、平均コスト
- **インスペクタ**: ベルト上のトークンにホバーで値と伝票を表示。機械の処理中状態・詰まりの原因を表示
- **検証パネル**: ブループリントに手入力の引数を与えて単体実行し、結果とステップ数を見る
- **チュートリアル**: T0 の契約を進行に沿ったガイドにする(`+2` を作る → 帰納炉で `add` を作る → カプセル化する)
- **表示**: トークンは値を数字で表示(大きい値は指数表記)。機械はアイコン+関数名

### 5.1 ビジュアルデザイン

方向性は **「方眼ノートに鉛筆とペンで書いた計算ノート」**。盤面は方眼紙、機械はペンで描いた箱、ベルトは矢印つきの手描き線、トークンは丸で囲んだ数字。独自のデザイン言語は作らず、既存のデザインシステムをそのまま採用する。

#### 採用するデザインシステム

| 対象 | 採用 | ライセンス | 役割 |
|---|---|---|---|
| HUD(ボタン、カード、タブ、モーダル、フォーム、バッジ等) | **PaperCSS** 1.9 | ISC | UI コンポーネントの見た目・余白・色の基準。これを唯一の UI 規範とする |
| 盤面と図形(機械、ベルト、枠線、ハッチング) | **Rough.js** 4.6 | MIT | 手描き風の線・塗りを生成する。盤面の全図形と、PaperCSS にない部品(研究ツリーの線、進捗バー等)に使う |
| 和文フォント(本文・数値) | **Klee One** | SIL OFL 1.1 | ペン字の教科書体。小さいサイズでも読める |
| 和文フォント(見出し・機械ラベル) | **Zen Kurenaido** | SIL OFL 1.1 | 手書き感の強い書体。大きめのサイズに限定して使う |

- いずれも商用利用・改変・再配布が可能。ライセンス表記を `THIRD_PARTY_LICENSES.md` とゲーム内のクレジット画面に載せる
- フォントは Fontsource 経由で自前ホスティングする(外部 CDN に依存しない)。和文は unicode-range 分割で必要なサブセットだけ読み込まれる
- 不採用: **wired-elements**(MIT、手描き風 Web Components)は 2022 年以降更新がなく RC 版のままのため。PaperCSS も 2023 年が最終リリースだが、純 CSS で依存がなく、リポジトリに取り込んで固定できるので問題にしない

#### 適用ルール

- **色**: PaperCSS のパレット(紙の白、インクの黒、primary / secondary / success / warning / danger / muted)だけを使う。独自の色は足さない。グラデーション・ドロップシャドウの追加・ガラス風の半透明・ネオン発光は使わない
- **意味づけ**: 色は状態にだけ使う(正解 = success、不正解 = danger、暴走・詰まり = warning、定理化済み = secondary)。伝票の区別は色ではなく、トークンの丸の線種(実線・破線・二重線)と小さい番号で示す
- **線**: 盤面の図形は Rough.js の単一設定(roughness・線幅・ハッチング角度を定数化)で描き、機械ごとにばらつかせない
- **塗り**: ベタ塗りは使わず、ハッチング(斜線)で表す。稼働中の機械はハッチングが濃くなる
- **動き**: 手描きの揺らぎは、同じ図形を 3 通りに描いた版を低速(4fps 程度)で切り替えて表現する。常時ではなく、稼働中の機械と選択中の対象だけに限る
- **アイコン**: 絵文字とアイコンフォントは使わない。機械の表示は関数記号(`Z`, `S`, `P`, `R`, `μ`)と名前の手書き文字で行う
- **ダークテーマ**: PaperCSS 標準のダークモードを使う(黒板風)。独自配色は作らない
- **アクセシビリティ**: 本文は 16px 以上、文字と背景のコントラスト比 4.5:1 以上。`prefers-reduced-motion` で揺らぎを止める

## 6. 技術選定

| 領域 | 採用 | 理由 |
|---|---|---|
| 言語 | **TypeScript**(strict) | 項・アリティ・セーブデータの型安全性。`bigint` を標準で使える |
| ビルド | **Vite** | 設定が少なく、Web Worker と静的ホスティングにそのまま対応 |
| パッケージ管理 | **pnpm**(Node 22) | 開発環境に導入済み |
| UI | **React + Zustand** | パネル・ツリー・一覧などの HUD は宣言的 UI が向く。Zustand はシミュレーション外の UI 状態に限定して使う |
| スタイル | **PaperCSS + CSS Modules** | §5.1 のデザインシステム。クラスを React コンポーネントで薄く包んで使う。ユーティリティ CSS は併用しない(見た目の規範を 1 つに保つ) |
| 盤面描画 | **PixiJS(WebGL)+ Rough.js** | 数千個のベルト上トークンをスプライトバッチで描ける。Rough.js は毎フレーム描画には重いので、起動時にオフスクリーン Canvas へ描いてテクスチャアトラス化し、PixiJS はスプライトとして貼るだけにする |
| フォント | **Klee One / Zen Kurenaido**(Fontsource) | §5.1。盤面上の数字は PixiJS のビットマップフォントに変換して描く |
| シミュレーション | **自前の純 TS コア + Web Worker** | 固定 tick の決定論的シミュレーションを UI スレッドから分離する。重い項評価で描画が止まらない |
| 数値 | 値は **`bigint`**、通貨は **break_infinity.js** | 値は正確さが必須。通貨は桁数だけ分かればよく速度優先 |
| 保存 | **IndexedDB(idb-keyval)** + 文字列エクスポート(lz-string) | localStorage の容量上限を避ける。手動バックアップ・共有用に文字列化 |
| テスト | **Vitest + fast-check** | 項評価器はプロパティテスト向き(例: 自作 `add` とネイティブ加算の一致) |
| Lint / Format | **Biome** | 1 ツールで完結 |
| 配布 | **GitHub Pages**(GitHub Actions) | 完全静的サイト。サーバー不要 |

### 6.1 採用しなかった選択肢

- **ゲームエンジン(Phaser / Godot / Unity)**: 本作は物理・アニメーションより UI とロジックの比重が大きく、エンジンの恩恵が小さい
- **Rust + WASM のシミュレーションコア**: 性能余地はあるが、初期は開発速度を優先する。コアを純 TS・DOM 非依存にしておき、ボトルネックが実測されたら差し替える
- **DOM / SVG での盤面描画**: トークン数が増えると破綻する

## 7. アーキテクチャ

```
src/
  core/        純粋ロジック(DOM・Worker 非依存、単体テスト対象)
    term.ts        項の型、アリティ検査、表示
    eval.ts        インタプリタ(ステップ予算つき、メモ化)
    catalog.ts     カタログ関数(ネイティブ実装・閉形式コスト・契約定義)
    extract.ts     盤面範囲 → 項(カプセル化)
    parse.ts       項のテキスト記法 ⇄ 項(項エディタ)
    schema.ts      図式(関数スロットつき項)と展開
    verify.ts      検査(検査入力の生成、参照実装との照合、最小反例)
  course/      不完全性コース(符号化、Q の構文と証明の参照実装、入力生成器、証明ノートの定義)
  sim/         盤面シミュレーション
    world.ts       グリッド、機械、ベルト、トークン
    tick.ts        固定 tick 更新
    contracts.ts   入力港・納品港・報酬
    economy.ts     通貨・研究・オフライン進行
  worker/      Worker エントリと通信プロトコル
  render/      PixiJS による盤面描画
    sketch.ts      Rough.js で図形を描きテクスチャアトラスを生成(線の設定はここに集約)
  ui/          React HUD(PaperCSS のクラスを包んだ部品)
  save/        シリアライズ、バージョン移行
  i18n/        文言辞書
```

### 7.1 シミュレーション

- **固定 20 tick/秒**、決定論的(乱数はシード付き、tick 順序固定)
- Worker がワールド状態を保持し、メインスレッドとはメッセージで通信する
  - メイン → Worker: コマンド(`place`, `remove`, `rotate`, `setSlot`, `encapsulate`, `acceptContract`, …)
  - Worker → メイン: スナップショット(毎 tick。トークン位置は TypedArray で転送)とイベント(納品、定理化、警告)
- 描画は直近 2 スナップショットを補間して 60fps で表示する
- 更新順序: 納品港 → 機械(出力側から)→ ベルト(下流から上流へ)→ 入力港。これで 1 tick に 1 マスの移動と詰まりの伝播が一意に決まる

### 7.2 項評価器

- 再帰呼び出しではなく **明示スタックの反復実装**(深い帰納でのスタックオーバーフロー回避)
- **ステップ予算**: 評価は予算を受け取り、尽きたら中断状態を返す。機械は複数 tick にまたがって評価を継続できる
- **メモ化**: ブループリント単位で `(引数) → (結果, コスト)` を LRU キャッシュ。契約の入力範囲は有界なので高ヒット率が期待できる
- 定理化済み `Ref` はネイティブ実装へ直接ディスパッチする
- 帯域幅超過は評価中に検出して打ち切る

### 7.3 主要データ型(概略)

```ts
type Term =
  | { kind: "Z" }
  | { kind: "S" }
  | { kind: "P"; n: number; i: number }
  | { kind: "C"; f: Term; gs: Term[]; arity: number }
  | { kind: "R"; g: Term; h: Term }
  | { kind: "M"; f: Term }
  | { kind: "Ref"; id: BlueprintId };

type Blueprint = {
  id: BlueprintId; name: string; arity: number;
  term: Term; layout?: LayoutSnapshot;
  theorem?: CatalogId;            // 定理化済みなら対応するカタログ関数
};

type Token = { value: bigint; job: JobId | null };

type Contract = {
  id: ContractId; target: CatalogId; arity: number;
  inputRange: [bigint, bigint][]; rewardPerDelivery: Decimal;
  streak: number; delivered: number;
};
```

### 7.4 セーブデータ

- バージョン番号つき JSON(`bigint` と `Decimal` は文字列化)
- 読み込み時にスキーマ検証 → 旧バージョンは移行関数を順に適用
- 30 秒ごと+タブ非表示時に自動保存。手動エクスポート/インポートあり

## 10. 未決事項とリスク

| 項目 | 内容 | 方針案 |
|---|---|---|
| 伝票方式の分かりやすさ | 伝票による同期はプレイヤーに見えにくい | インスペクタで色分け表示。M3 でプレイテストし、難しければ「機械は FIFO 同期のみ・並列化は専用機械に限定」へ単純化 |
| 帰納炉の内部並列化 | スロット式は盤面の工夫の余地が小さい | v1.0 以降で「帰納炉に盤面のループ区画を接続する」上級モードを検討 |
| 定理化の判定 | 規定回数の正解は「証明」ではなくテスト | ゲーム上の演出として割り切る。カタログ外の関数には適用しない |
| 自作関数の評価コスト | 定理化されない深い項はインタプリタで重い | ステップ予算+メモ化+グローバル上限。実測で不足なら WASM 化 |
| 不完全性コースの評価可能性 | `repr` を通した論理式とゲーデル文がどこまで大きくなるか、プレイヤーの項を現実的な時間で検査できるかが未実測 | M8 前に参照実装で試作して実測。大きすぎる場合は `repr` の対象を `diag` と `prf` に必要な構成子に絞る、または G4 を段階的な小課題に分割する |
| 不完全性コースの正確さ | 定理の主張・補題の引用範囲・Q の公理と論理公理の選び方に誤りがあると価値を損なう | 標準的な教科書の定式化に 1 冊決めて準拠し、ノートに出典を明記する。数理論理に詳しい人のレビューを受ける |
| 図式の分かりやすさ | 関数スロットつきブループリントは抽象度が高い | G0 を独立したチュートリアルにし、有界和 1 つを手で導出させてから一般化する |
| 探究モードの手応え | 待ち時間をなくすと達成感が薄くなる恐れ | 反例表示と証明ノート・到達記録を報酬の中心にする |
| 手書き書体の可読性 | 小さい数字や長い項の表示が読みにくくなる恐れ | 本文・数値は Klee One に限定。M3 で実機確認し、不足なら項の表示だけ等幅書体にする |
| 手描き風の描画負荷 | Rough.js の図形はテクスチャ化が前提で、ズーム時にぼやける | アトラスを 2 段階の解像度で用意する |
| バランス | 契約単価・機械速度・定理化条件 | 数値はすべてデータファイル(`catalog.ts` 等)に集約し、M5 以降に調整 |
| T5 万能関数の難度 | 実装は相当に難しい | 途中の部品(対関数、列操作、1 ステップ関数)を個別契約にして段階化 |
